### 实现过程中发现的两个真实设计问题（已修，值得记录）

#### ① 为什么探针必须**整版注入**记忆，而不能靠关键词检索

标准探针问题是「你还记得我之前说过的那件事吗？」—— 它**刻意不点名事件**
（点名会引导模型，污染结果，见 docs 的 P1 风险）。

但关键词检索要靠词重叠才能召回。一个不点名的问题几乎必然 0 命中，
于是探针注入的是**空记忆** —— 测出来的只是「模型对空上下文怎么答」，
**完全测不到记忆，实验会得出假结论**。

修法：探针走整版注入（`memory.render_full_version`），
把该版本全部条目原样给它，不做筛选。关键词检索结果仍单独落进 `retrievals` 表，
`method` 标为 `probe_full_version`，便于事后区分两种注入方式。

#### ② 关键词检索的能力边界（如实记录，非 bug）

实测确认：**同义但用词不同的表述，字符 n-gram 交集可以为空**。

| 表述 A | 表述 B | 2-gram 交集 |
|--------|--------|------------|
| 上夜班 | 晚上工作 | **空集**（只共享单字「上」） |

`上夜班` 切出 `上夜/夜班`，`晚上工作` 切出 `晚上/上工` —— 一个都不重合。

这是「不用 embedding」的必然代价，`docs` 已经论证过这个取舍
（embedding 会引入与被测对象无关的语义相似度变量，让「记不清」和「没召回」无法归因）。

**因此检索器采用这个口径**：
- 单字重叠**不足以**判定相关（否则「今天天气」会因「天」「上」「过」被误召回）
- 必须至少有一次 ≥2 字的命中
- 但仅靠 n-gram 时，措辞差异大的同义查询会召回失败

**这个限制必须在 Phase 11 实验分析时记住**：探针回答不出某件事，
可能是「记忆里没有了」，也可能是「检索没召回」。`retrievals` 表就是为区分这两者而存在的。

原文逐字（**不可改写**）：

> 上个月我在花市买了一盆茉莉，卖家说是去年的苗。它特别怕冷，冬天得搬进屋里。我把它放在书桌旁边的窗台上，大概六月份才会开花。前两天掉了几个花苞，我有点心疼。

### 为什么基准事件走专门的固化命令，而不是走聊天

`raw_event_001` 是实验的**基准事实**，要求逐字稳定、ID 固定、可重复重建。
走聊天做不到：会生成随机 `turn_id` / `event_id`，原始事件文本还会随对话上下文变化。

所以它从受控定义文件固化，人工标注清单也从同一份定义生成 —— **两处同源，不会互相漂移**。

### 证据等级标注（重要）

四条事实里，**B2 标为 `UNKNOWN` 而不是 `FACT`**：

原文是「**卖家说**是去年的苗」—— 二手转述，不是用户自己的判断。
这是四条里最容易发生**证据等级漂移**（UNKNOWN → FACT）的一条，
Phase 6 的 Changelog 必须能发现这类类型变化。

### 时间锚点

原文用了「上个月」「前两天」「去年」「六月份」这些相对时间词。
已锚定：上个月 ≈ 2026-09、前天 ≈ 2026-10-05、去年 ≈ 2025、六月份 ≈ 2026-06。
不锚定就无法判定「上个月」漂成了哪个月，也无法区分时间漂移是模型问题还是时间自然流逝。

## 3.7 修复：`selftest --clean` 会删除真实实验数据（**严重**）

这是本次最严重的缺陷，**在固化基准事件后才暴露出来**。

### 现象

固化 `raw_event_001` 之后跑 `python src\main.py selftest --clean`，基准事件被删除：

- 事件文件 `raw_event_001.json` 消失
- 数据库里的登记行也消失
- 更糟的是曾出现**孤儿状态**：文件还在但数据库无记录，`verify` 报「未登记」

### 根因（三层，逐层才挖到底）

| 层 | 缺陷 | 为什么危险 |
|----|------|-----------|
| 1 | `_clean` 用 `RAW_EVENTS_DIR.glob("*")` 无差别删除目录内容 | 连归档说明一起删（早期已修） |
| 2 | 改为「按数据库登记的事件 ID 删除」后，取的是**删除时刻表里的全部事件** | 基准事件也在表里，于是被一起删 |
| 3 | `conn.close()` 排在 `_clean()` **之前** | `_clean` 的 DELETE 抛 `sqlite3.ProgrammingError`，清理**静默失败**，留下残留数据与孤儿行 |

第 3 层尤其隐蔽：进程非零退出，但如果只看被过滤的输出就会以为「自测通过、清理完成」。

### 修法

1. **开跑前先记下已存在的事件 ID 与会话 ID**，只清理「跑完才出现」的那些
2. **不再 `rmtree` 整个 `conversation/` 目录** —— 改为只 `DELETE` 属于本次自测会话的行，
   数据库文件始终保留
3. **硬保护 `raw_event_001`** —— 它在 `_clean` 里被显式跳过
4. **调整 `conn.close()` 到 `_clean()` 之后**
5. 费用流水改为「只摘掉本次自测那几行」，不再整文件删除
6. 自测的项数不再受既有事件影响（只校验自己新建的事件），稳定为 13 项

### 验证

修复后重跑破坏性测试：

```
共 13 项，通过 13 项，失败 0 项。
已清理测试数据：2 个事件文件、4 轮对话、4 条调用记录、4 条费用流水。
已保留的既有会话：sess_fixture
（数据库文件本身、既有真实数据、memory/versions/ 均未被触碰）
```

`raw_event_001` 的**文件与数据库行均完好**，文件哈希与清理前一致，
`verify` 报「原始数据未被改动」，无孤儿记录。

### 教训

我把两次失误合并成了同一个模式：**拿真实数据库去跑破坏性命令**。
正确做法是先把库复制到临时目录，在副本上测。本文件 §3 记录的 3 轮对话被清，
以及本节基准事件被删除，都是这个原因。

## 4. 本次发现的问题（已记录，**尚未修复**）

经查证：以下都是**真实存在**的现象，不是误报。

### 问题① `deepseek-flash` 是推理模型，思考 token 计入输出计费

模型先在 `message.reasoning_content` 产出思考过程，再填 `content`。实测：

| 请求 | 输出 tokens | 其中 reasoning | 占比 |
|------|-----------|---------------|------|
| 「在吗」（正式对话路径） | 71 | 66 | 93% |
| 「我今天有点累…」 | 109 | 92 | 84% |
| 「你叫什么名字？」 | 13 | 0 | 0% |
| `doctor` 的 `max_tokens=16` 探针 | 16 | **16** | **100%** |
| 探针改用 `max_tokens=200` | 53 | 50 | 94% |

**影响**：

- 正式对话（`settings.json` 的 `max_tokens=800`）**实测完全正常**，3 轮均返回有效内容，
  无截断风险
- 但 `docs/feasibility.md` 第 6.2 节的成本模型按「普通对话每次输出约 0.5k」
  估算，**未计入思考 token**，因此该估算偏低。实际输出量约为可见文本的数倍
- 回复前有额外延迟（本次实测约 1.3–2 秒）

**建议**：Phase 5 之前不必处理；做成本预算时把输出 token 按可见文本的 3–5 倍估。

### 问题② `doctor --online` 可能在返回空回复时误报通过

`doctor.py` 第 114 行用 `max_tokens=16` 发最小请求。推理模型的 16 个 token 会被思考
过程全部吃光 → `finish_reason = "length"`（截断）→ `content` 为空字符串。

而 `doctor.py` 第 116 行的通过判据只检查「有没有抛 `LLMError`」，**不检查文本是否非空**，
所以在 §2 那次自检里它输出了 `返回「」` 却仍然判 OK。

**影响**：结论方向没错（连通性确实可用），但判据偏弱，无法发现「模型返回空内容」类故障。

**建议修法**（未实施）：把 `max_tokens` 提到 64，并增加 `bool(reply.text.strip())` 断言。

### 问题③ `doctor --online` 自检调用不进费用账本

`doctor.py` 直接 `LLMClient(...).send(...)`，未走 `chat.send_once()`，
因此**既不写 `api_calls` 表，也不写 `logs/ledger.jsonl`**。

**影响**：`python src\main.py cost` 的汇总会**系统性偏低**。这属于《project-spec》§25
第 8 项「成本能够记录」的一个缺口。

**建议修法**（未实施）：`doctor --online` 成功后调用
`storage.record_api_call()` + `pricing.append_ledger()` 记账。

### 附带：一处显示 bug（非功能问题）

`doctor` 输出 `[OK  ] .env 存在：已创建，但 LLM_API_KEY 还是空的` ——
这行文字**是错的**（Key 已正确填入并验证可用）。原因见 `doctor.py` 第 61–65 行：
该检查只看 `.env` **文件是否存在**，未检查文件里 `LLM_API_KEY` 是否有值，
提示语却在两种情况下都用了「还是空的」这句措辞。
