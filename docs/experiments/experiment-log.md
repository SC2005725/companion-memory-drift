## 3. ⚠️ 位置项：用户主动改口（重要，勿判为漂移）

| | |
|---|---|
| 基准原文写的 | 「书桌旁边的窗台」（B4a） |
| 用户正式对话中说的 | 「放阳台」（seq 24） |
| 用户事后确认 | **以「阳台」为准**（明确表示这是有意改的） |

**v001 里两条并存、且都标成 `FACT`：**

```
[FACT] 用户把这盆茉莉放在书桌旁边的窗台上。   来源=raw_event_001
[FACT] 用户把这盆茉莉放在阳台。               来源=（无）
```

**这不是代码 bug** —— 模型的输入里同时有基准原文和用户的新说法，它无从判断哪个作数。
**这正是实验要观察的现象**，只不过这次的原因是「用户改口」，不是「记忆变质」。

**判定口径**：

| 记忆 / 回答里出现的说法 | 应判定为 |
|---------------------|---------|
| 阳台 | **正确** —— 用户已改口 |
| 书桌旁边的窗台 | **陈旧** —— 来自基准原文，用户已更正 |
| 两者同时出现且未区分 | 需人工复核 —— 可能是记忆把两处地点并成了一处 |

**为什么必须记这一条**：若不记，将来对照清单会把「阳台」误判成模型编造，
或把「书桌旁边的窗台」误判成记忆保留完好。**两者都会得出错误结论。**

### 处置方式（重要）

**更正必须来自对话，不能由助手编辑记忆文件。**
若用编辑工具手改 v002 的内容，它就不再是「模型的记忆版本」，实验会失真。

所以：需要用户在对话中亲口告诉小满位置已更正，然后再 `consolidate` 生成 v002
—— **「它会不会真的改过来」本身就是第一个观察点。**

## 4. v001 → v002（第二次整理）结果

花费 0.009907 元。**条目数 19 → 10**（模型把事实重新分段、合并）。

### 好消息

- **更正被正确捕捉**：
  ```
  [FACT] 用户最初说茉莉放在书桌旁边的窗台上，后来表示这是记错了。
  [FACT] 用户更正：茉莉其实是放在阳台。
  ```
- **零伪造来源**：v001、v002 引用的全部事件 ID 都真实存在（共 7 条事件）。
- **B2 仍未被拔高**：依旧标 `UNKNOWN`，且新增了「（用户未自行确认）」的限定。

### ⚠️ 发现一个方法论层面的根本限制

**模型每次整理会重新分段，条目之间不再是一一对应关系**（19 → 10 条）。
这导致 changelog 的配对算法无法可靠工作，实测出现明显错误的配对：

```
用户名叫（网名）        →  用户在做「最小聊天原型」
用户今天看了三本书   →  用户的聊天配置是：人格为「小满」…
用户是头一回养茉莉   →  用户运行时遇到 Python 报错：…main.py 第 446 行…
```

**为什么会错**：11 条 removed、只有 5 条 added，贪心配对在把好的配完后，
只能拿剩下的条目互相硬凑。

**已做的修复**（`src/changelog.py`）：

| 修复 | 说明 |
|------|------|
| 新增 `containment()` 方向性度量 | 原用的对称 Dice 会惩罚「新句是旧句超集」的情况：「这盆茉莉特别怕冷」→「这盆茉莉特别怕冷，冬天得搬进屋里」只得 0.11 分，明明是**信息被完整保留** |
| 新增 `absorbed`（被并入）分类 | 旧句内容留存 ≥85% 但新句更长 → 归为「被并入 / 被扩展」，不再误判成「换说法」 |
| 配对判据改用 containment | 不再用对称相似度做配对门槛 |

修复后「被并入」正确识别（留存 0.96、0.94），**但剩下的错误配对无法靠调算法解决** ——
因为问题不在算法，在「一份信息被切成几条」本身是可变的。

### 应对方式：改用「基准事实存活率」作为主要对比手段

条目级 diff 不可靠，但实验真正要问的问题可以直接量：

> **对每条基准事实（B1–B4c），它在 v001 / v002 / v003 / 最终回忆里还在不在？**

这是可判定、可人工复核、不依赖配对的度量。changelog 保留作为辅助
（它能可靠抓到的三类：`type_changed` 证据等级漂移、`merged` 事实合并、
`removed` 真丢失），但**不把它的配对结果当作结论**。

### ⚠️ 一个必须说明的读数陷阱

报告里「最终回忆」一列显示 B1/B2/B3/B4b **未提及** —— **这不能读作「记忆丢失」**。

原因：探针问题是「你还记得我之前说过的那件事吗？」，它**刻意不点名事件**
（点名会引导模型、污染结果，见 docs 的 P1 风险）。
一个开放问题、一次回答，本就不可能列出全部 6 条事实。

而 **v003 里 6 条事实全部在册**（存活率 100%）。所以正确结论是：

> **开放探针只自然带出 2 条（B4a、B4c），但记忆本身完整无缺失。**

若要量「每条事实能否被主动回忆」，需要**逐条点名**的补充探针
（如「那盆茉莉的事你还记得多少？」）。但那与「不点名」原则冲突，
必须在报告中**明确标注为补充探针**，不能与固定问题混用。

## 6. Phase 6/7/8 真实聊天测试（2026-10-08）

### 测试结果

**13 轮新对话**（seq 68–80），花费约 0.009 元（累计 0.109599 元）。

| 层 | 结果 |
|----|------|
| **关系** | ✅ 事件正确捕获（seq 73「谢谢你，跟你聊挺舒服的」→ positive）。信任 21.27 / 亲近 19.31 / 熟悉 18.67 |
| **心跳** | ✅ 正确判断「刚聊完 → 等待」（空闲 0.1h < 阈值 12h） |
| **用户模型** | ❌ **两个真 bug，已修**（见下） |

### ⚠️ 用户模型的两个真 bug（已修）

#### Bug 1：修正打偏了

用户说「我没说过我不太爱说话」（seq 80），**应该作废** `我是那种不太爱说话的人`。
实际却作废了 `我一般晚上才有精神` —— **完全正确的那条被误伤**。

**根因**：两条候选与修正句的 2-gram 重叠分**打平（都是 2）**，
代码退化成「取较新的一条」→ 选中错误目标。

**修法**：先剥掉修正词本身（「我没说过」）再算**覆盖率**；**要求唯一最高分，并列就不猜**
（返回 None，宁可修正不生效也不误伤）。

#### Bug 2：修正句自己被当成一条用户主张

`我没说过我不太爱说话` 被存成一条 `confirmed` 生效条目，
于是模型同时持有「我不太爱说话」和「我没说过我不太爱说话」**两条互相矛盾的主张**。

**修法**：修正条目标记 `is_correction`，`active_items()` 排除它们 ——
修正的作用是「指向一条既有判断并作废它」，它本身不是关于用户的判断。

#### 修复过程中发现的第三点

Bug 1 修了一半后又发现：把候选**限死在 inferred** 会让「用户否定一条 confirmed 判断」
时修正**完全失效**。而「模型记着用户明确说过 X、用户却说没说过」正是**最该发现的矛盾**。
所以改为：**推断条目优先，但明确说过的也能被修正**。

### 真实数据的修复方式（不手改快照）

出错的那份快照（v003）内容有误。**没有手工编辑 JSON** ——
手改会让快照与事件流对不上。改用**重放**：从对话表里的用户原话重新推演一遍
（证据都在对话表里，可复现），生成 v004，并记一条 `repair` 事件保持审计链完整。

重放结果正确：

```
[作废] 我是那种不太爱说话的人
[生效] 我一般晚上才有精神     ← 不再被误伤
```

结果：3 条条目（生效 1、已修正 1、修正指令 1）。备份留在 `%TEMP%\user_model_backup_*`。

### 补的回归测试

这个 bug **真实聊天才发现，自测没抓到**，所以补了 8 项（89 → **97 项**）：

- 修正必须打中正确目标（复刻真实场景：1 confirmed + 1 inferred，否定 confirmed 那条）
- 不误伤另一条
- confirmed 条目也能被修正
- 修正指令本身不作为生效条目
- 目标不明（并列）时不误伤任何一条

### 教训

**离线自测的「确定性上下文」覆盖不到真实数据的分布。** 我为修正功能写的自测用的是
「只有一条推断」的场景，所以「两条打平」这条路根本走不到 —— **真实聊天一跑就暴露了**。
这与之前 4 个缺陷是同一个模式。

## 7. ⚠️ 记忆捕获完整性缺口：身份信息（2026-10-08 发现）

### 现象

用户**三次**说自己叫「（网名）」（seq 10、69、89），系统始终不记得：

| 轮次 | 小满的回答 |
|------|-----------|
| seq 88 | 「不知道。你还没跟我说过名字。」 |
| seq 89 | 「没有，这是你第一次说。」 |

### 两层原因

**① 触发词没覆盖身份句式。** 「我叫（网名）」不命中任何触发词 → **从未进入 Raw Event 层**。
实测：`detect('我叫（网名）')` → `hit=False`。

**② 已进入记忆的那条在整理时丢了。** v001 里**有**「用户名叫（网名）。」，
但 v002、v003 里**都没有了**。

所以这不是「检索没召回」，是**记忆里真的没了** —— 属于**记忆丢失**。

**责任在助手**：扩充触发词时只盯着茉莉的 B1–B4，漏掉了最基本的身份信息；
且当时看到 v001 有「用户名叫（网名）」、v002 没了，只当作「非基准内容的正常丢失」，
**没有意识到"AI 该记住的第一件事就是用户的名字"**。

### 用户对本次事故的定性（比助手原结论更准确，采纳）

> 「（网名）」未能被触发词捕获，未进入完整 Raw Event 链；已有的 v001 相关记录又在
> v002 consolidation 中消失，因此属于真实的信息丢失。
> **该问题不影响原 18/18 基准事实的统计，但说明原实验只验证了基准事实进入系统后的
> 存活率，没有覆盖自然对话中的记忆捕获完整性。**

**这个补充很关键**：18/18 衡量的是「已注入的基准事实在各版本里还在不在」，
它**测不到「该记的东西有没有被抓进来」**。这是原实验的方法论盲区，必须写进结论。

| # | Bug | 后果 | 严重度 |

### Bug 4 最值得记录：写了却召不回来

记忆里明明有「用户自称叫（网名）」，但问 **「我叫什么」召不回来**。

**根因**：名字条与查询**零 2-gram 重叠**（`叫什`/`么名` vs `用户`/`自称`/`（网名）`），
连 `strong` 门槛都过不了，**压根进不了候选**。而「用户在意自己是否被记住…
记得他叫**什么**名字」这条推断因含 `叫什`/`么名` 反而命中。

**问名字永远拿不到名字 —— 写了跟没写一样。**

修复过程本身也踩了两个坑，值得记下：

1. **第一版放宽太粗**：「条目含『叫』或『名字』」就放宽 → **「用户点咖啡一般是下午叫外卖」也被当成身份条**，在问名字时排到第 1 位。
2. **第二版加权不够**：名字条进了候选但只排第 2，被那条推断（纯靠 2-gram 重叠拿 13.30 分）压住。

最终判据：**姓名式模式** `叫|名字是|名字叫` 后紧跟 2–4 个非标点字符，且不能是
「什么/啥/外卖/出来」这类；身份查询下给这种条目加 30 分（高于任何纯 2-gram 重叠分）。
实测：5 种问法**必定排第 1**，无关查询**零误召回**。

### 修复方式

| Bug | 修法 | 位置 |
|---|------|------|
| 1 | 加疑问句防线（句末问号或含疑问词）→ 不产生信号 | `user_model.py` |
| 2 | 补纠正句式：`纠正/更正/我其实/我之前说错/我说错了` | `settings.json` |
| 3 | 自我描述词补 `我叫/我的名字/我名字/我姓` | `settings.json` |
| 4 | 姓名式模式 + 身份查询加权（见上） | `memory.py` |
| 5 | 关系正面词补 `跟你聊/跟你聊天/喜欢跟你/聊得挺` 等 | `settings.json` |
| 6 | 主张**只取关键词起头的片段**（`_extract_claim`）+ 同主张去重 | `user_model.py` |

另：把「**偏好更新**」（咖啡→茶）与「**事实否定**」（你记错了）的留痕理由**区分开** ——
两者都作废旧条目，但语义不同，理由必须写准才好人工复核。

远低于 1M 上下文；单次成本约 0.13 元，属「读一个大文件」的合理代价）。

## 10. 独立复核发现的 P0 缺陷：`take_note` 同秒覆盖（2026-10-08）

### 来源

用户**独立解压归档包实跑**后发现，不是助手自查出来的。
（这是本项目第一次由外部复核抓到的缺陷 —— 值得记录这个事实本身。）

### 现象

`take_note` 原用 `note_YYYYMMDD_HHMMSS.md` 命名。**同一秒内连续记两条笔记时，
第二条直接覆盖第一条**：

```text
第1次: 已记下 note_20261008_203045.md；已进入原始事件层（raw_event_62b1af11）
第2次: 已记下 note_20261008_203045.md；已进入原始事件层（raw_event_15c96c9d）
→ 新增文件 1 个，新增原始事件 2 条
→ 存活文件内容是「第二条」
```

**助手独立复现确认了这个结果。**

### 为什么这是真问题

出现**数据一致性问题**：工具调用 ✓、原始事件 ✓、文件 ✗ 被覆盖。
「记下来」的承诺变成假的 —— 而 `take_note` 正是唯一与项目本体耦合、
以「真的留痕」为卖点的工具。

注意 **Tool Loop 支持一轮内多次调用**（`max_iterations=5`），
所以同秒两次调用是**可达路径**，不是理论边界。

### 修法（采纳用户建议）

**改用 `event_id` 命名文件**：`note_<event_id>.md`。

```text
第1次 → note_raw_event_5ba33034.md
第2次 → note_raw_event_dbd6b9e9.md
→ 2 个文件 / 2 条事件，内容互不覆盖，文件名与事件天然一一对应
```

顺带把顺序**反转**了：原来「先写文件，再建事件」，现在「**先建事件，再据其 ID 写文件**」。
这样事件建不出来时**直接返回失败、不写文件** ——
宁可没有这条笔记，也不留下一个没有对应事件、无法追溯的孤儿文件。

### 顺带修正的说法过头问题

工具描述原写「会写入笔记文件并进入长期记忆」，**不准确**。
实际路径是 `take_note → notes/*.md → Raw Event`，
**真正变成 Memory 还要再过一次 `consolidate`**。
已改为「写入笔记文件，并进入原始事件层（后续可被记忆整理纳入长期记忆）」。

### 回归测试（56 → **62 项**）

| 检查 | 锁住什么 |
|------|---------|
| 同秒两条产生 2 个文件 | 覆盖 bug 本体 |
| 同秒两条产生 2 条原始事件 | 与文件数对得上 |
| 两个文件内容各不相同 | 没有谁被静默覆盖 |
| 文件名与 event_id 一一对应 | 命名规则本身 |
| 返回没有夸大成「已进入长期记忆」 | 说法过头的回归 |

## 11. 独立安全审计：工具层 6 个真问题（2026-10-08，全部已修）

### 来源

派了三个独立审计子代理（各自专注记忆/工具/状态机）。
**工具层审计报告返回了实质结果**，其余两个被中途叫停（原因见本节末）。

### 🔴 1. 敏感文件名单可用「加合法扩展名」绕过 —— 真的读出密钥

原实现是**精确名匹配**：`DENY_NAMES = (".env", ".env.local", ...)` +
`target.name in DENY_NAMES`。

审计实测：`.env.txt`、`.env.bak`、`.env.json`、`credentials.json`、`credentials.yaml`、
`secrets.yaml`、`id_rsa.txt`、`id_ed25519.md`、`api_key.txt`、`token.txt` ——
**21 个变体里 20 个读出明文**，唯一拦住的是精确名 `.env`。

**为什么这个漏洞特别严重**：`.env` 这类文件**天生就是靠变体名管理的**
（`.env.local` / `.env.production` / `.env.bak`）。用精确名单去堵变体名，等于没堵。

**修法**：改前缀/片段匹配（`is_sensitive()`）—— 文件名以 `.env`/`.ssh`/`.git` 开头即拒；
含 `credential`/`secret`/`api_key`/`id_rsa`/`.pem`/`token` 等片段即拒；
路径中任一目录名命中同样拒。**15 个变体全部拦住，普通文件不受影响。**

### 🔴 2. 深嵌套 JSON 打崩整轮对话

`"[" * 3000 + "]" * 3000`（**仅约 6KB**）让 `json.loads` 抛 `RecursionError`。
而原异常元组只捕 `(ValueError, TypeError)` —— **异常穿透 `parse_calls`，
最终打崩整轮会话**。

**修法**：① 解析前做括号深度预检（上限 200）；② 异常元组给全。
实测 3000 层不再抛异常。

### 🟠 3. 一个围栏块里放两个对象 → 静默丢全部调用

`_TOOL_BLOCK_RE` 把整块 `{...}\n{...}` 当一个 JSON 解析 → 失败 → **0 个调用**，
且不报错。而 `prompt.py` 明说「可以一次输出多个」—— **协议描述与解析能力矛盾**。

**修法**：块内改**按括号配对切分**（跳过字符串内的括号），一次拿全。

### 🟠 4. 坏围栏块连带吃掉后面所有合法裸对象

原实现只要**存在任意围栏块**，裸对象扫描就整个跳过 → 一个坏块毁掉整轮。

**修法**：围栏解析结果为空时才回退到块外裸对象扫描。

### 🟠 5. 正文里的 JSON 举例被当成真实调用执行，并从正文里删掉

`_LOOSE_RE` 在整个回复里无围栏扫描：模型或用户**举例、引用、写文档**时命中就会被真执行，
同时 `strip_calls` 把它从用户可见正文里删掉 —— **用户看不到发生过什么**。

**修法**：裸对象扫描**排除围栏内部**（先摘掉所有围栏再扫）；
`strip_calls` **只删围栏块**，不再删正文里的裸对象。

### 🟡 6. 权限检查只在 `call()`，绕过它就能跑本机代码

审计实测：`reg.call("run_python")` 被正确拒绝，但
`reg._tools["run_python"].execute({"code": ...})` **直接执行成功**。

**修法**：把权限与参数校验**下沉到 `execute` 外面**（`_install_permission_gate`）——
一个咽喉变两个，纵深防御。

### ✅ 审计确认**没有**被攻破的部分（如实记录）

- **路径包含性检查可靠**：`..`、多重斜杠、正反斜杠混用、绝对路径、`C:foo`
  驱动器相对、UNC（`\\?\`、`\\.\`、`\\localhost\C$`）、8.3 短名、大小写、
  尾随点/空格、NUL —— 全部正确拒绝或正确落在 root 内
- **符号链接 / junction 也无法绕过**：`mklink /J` 建的 junction 指向 root 外时，
  被 `Path.resolve()` 展开后正确判定越界
- 无 ReDoS（病态输入 100k 层耗时 0.0087s）
- 无无限循环（`MAX_ITERATIONS=5` 硬上限）
- `take_note` 文件名用 event_id，无路径注入

### ⚠️ 过程失误：我差点交付一个「假修复」

修 #2/#3/#4 时，我的新实现被**文件里遗留的旧定义覆盖**了 ——
同一个文件里出现了**两份 `parse_calls` / `strip_calls`**，Python 取后者（旧的那份）。

**新代码被塞进文件，但实际运行的是旧代码。** 幸好我逐个函数验证时报了
`RecursionError` 且 traceback 指向旧行号，才发现重复定义。

**教训**：改文件后不能只看「编译通过」，要**确认新定义真的生效**（我这次是靠
「修完还报同一个错」才警觉）。这也是「不静默失败」原则的一次体现 ——
如果我当时只看「编译 exit=0」就报告修好，交付的就是假的。

### 关于三个审计子代理

工具层那个报告完整返回；**另两个被中途叫停**，原因是发现工具层审计
**直接在真实项目上调用了 `take_note`**，往真实数据库写了一条测试事件
（`raw_event_bcd73ac7`「示例笔记」，已清理）。

我叮嘱过「不要修改项目文件」，但**没明确禁止写运行时数据** —— 这是指令疏漏。
教训：给子代理的约束要覆盖**所有副作用**，不只是「不要改文件」。

### 回归测试（69 → **78 项**）

新增 9 项，全部针对上面被攻破的点：15 个敏感变体、深嵌套、一块多对象、
坏围栏回退、正文不误删、execute 路径权限检查。

## 12. 正式实验期间修复的代码缺陷（会污染结论的那种）

这四条都是在真实数据上跑才暴露的，之前全部自测都没抓到。

| # | 缺陷 | 后果 | 修法 |
|---|------|------|------|
| 1 | 推理模型的思考 token 吃光 `max_tokens`，产出**空回复** | 探针若也如此，空回答会被记成「记忆丢失」，**直接伪造结论** | 检测 `finish_reason='length'` 且内容为空 → 自动用更大预算重试；仍为空则明确报错 |
| 2 | 整理任务预算不足。34 轮对话时思考单独吃了 **3201** token 仍未结束 | **Phase 5 核心功能完全跑不起来** | 按用途分别给预算：`chat=800 / consolidate=12000 / probe=800` |
| 3 | `chat.run_repl()` 会话头用 `mem.item_count`，而 `sqlite3.Row` 只支持下表访问 | **生成 v001 后一点「开始聊天」就崩** | 改用 `mem['item_count']`，并把会话头抽成 `print_header()` 以便测试覆盖 |
| 4 | `storage.recent_turns()` **不按会话过滤**，读整张表 | 新开一段会话会看到**上一段**的片段；不同阶段上下文混合，污染漂移归因 | 增加 `session_id` 参数并只取本会话历史 |

**共同教训**：这四条都是「只在特定状态下才走到的代码路径」。
自测覆盖的是「干净环境 + 假客户端」，走不到这些分支。
**真实数据一跑，它们全部现形。**

## 14. 一个必须记住的观察限制

当前 `config/settings.json` 的 `history_turns = 10`，即**本会话最近 10 轮对话原文
一直注入上下文**。因此：

- 在对话阶段，小满答对**可能靠的是「看着原文」**，而不是「记忆」
- 修复第 4 条缺陷后，历史**只取本会话**，所以跨会话不再泄漏

**所以正式观察点必须依靠 `recall` 探针** —— 探针**不注入任何历史对话**，
只给人格 + 指定记忆版本。这条隔离已在代码中落实并有测试锁住。

等对话轮数继续增长、早期内容自然掉出 `history_turns` 窗口后，
对话阶段的回答才真正开始依赖记忆。

## 15. Phase 11「长期运行实验」：容量实测 + 一次严重的数据事故

> 规范对 Phase 11 只有一行字（`Phase 11 / 长期运行实验`），没有详细章节。
> 所以这一节的结论是从**实测**推出来的，不是照抄规范。

### 15.1 优先级澄清

规范 §35 的优先级链：

```text
能运行 → 能持续运行 → 能记忆 → 能形成关系 → 能行动 → 能使用工具 → 能长期演化 → 能商业化
                  ↑ 我们在这
```

**「能持续运行」是第 2 优先级** —— 所以 Phase 11 的实质问题是
「这系统撑得住长跑吗」，而不是「再加什么功能」。

### 15.2 ⚠️ 先说结论：**目前做不到「无人值守的长期运行」**

三件事必须说清：

1. **每轮对话都要人手输入。** 系统没有任何调度器/定时器 ——
   `heartbeat` 只能手动跑 `python src\main.py heartbeat`。
   也就是说：**你不来，它就不动。**
2. **进程不常驻。** 命令行版本是脚本；网页界面要那个黑窗口开着。
   关掉即结束，没有开机自启、没有守护进程。
3. **因此「长期运行实验」在本版本上做不到** ——
   能做到的是「人在时持续可用」，不是「24 小时自己跑」。

要真做长期运行实验，缺的是**调度器**（定时触发 heartbeat + 定期自动 consolidate）。
那是一块新功能，尚未写。

### 15.3 容量实测（这部分是好消息）

用合成数据实测（**在临时副本上跑**，见 15.4 的事故说明）：

| 对话轮数 | 数据库 | 读历史 | 取 seq | verify 全量 | 界面侧栏 |
|---------|--------|--------|--------|------------|---------|
| 500 | 0.4 MB | 0.062 ms | 0.063 ms | 1.4 ms | 0.061 ms |
| 5,000 | 1.5 MB | 0.062 ms | 0.207 ms | 14.8 ms | 0.061 ms |
| 20,000 | 5.6 MB | 0.083 ms | 0.669 ms | 72.3 ms | 0.143 ms |

**结论：数据量不构成瓶颈。**

- 读历史**恒定 0.06–0.08 ms**（`conversations.session_id` 有索引，是唯一加过索引的表）
- 「取 seq」线性增长，但 2 万轮也只要 0.67 ms
- `verify` 是 O(n) 全表重算哈希，2 万轮 72 ms —— 但它是**审计工具、不是热路径**，可接受
- 界面侧栏（6 个 `COUNT(*)`）2 万轮 0.14 ms

**按每天 20 轮外推**：一年 7,300 轮 ≈ 5,000 轮量级，数据库约 2 MB。
**几十年也用不到需要加索引的规模。**

真正会无上限增长的是 `logs/ledger.jsonl` 与 `logs/run.log`（当前 64 KB / 40 KB），
但一年约 1.5 MB，也不构成问题。

### 15.4 🔴 事故：我把 50000 行合成数据写进了真实数据库

**这是本项目最严重的一次数据事故** —— 比之前任何 bug 都严重，因为直接毁数据。

**经过**：做 15.3 的容量测试时，脚本里写的是：

```python
paths.DB_FILE = Path(副本路径)      # ← 我以为这样就切过去了
c = storage.connect()               # ← 实际连的还是真实数据库
```

**根因**：`storage.py` 用的是 `from paths import DB_FILE` ——
这个写法在**模块导入时**就把值绑死了。之后改 `paths.DB_FILE` 对 `storage` 完全无效。

**后果**：`conversations` 表被写入 **50,000 行**合成数据（`u0`/`a0`…），
数据库从 472 KB 涨到 **13.8 MB**，真实对话记录被覆盖性删除。

（讽刺的是：我本来正是在做「长期运行」的容量测试，
却用一次测试毁掉了被测的数据。）

**恢复**：从 `%TEMP%\conv_before_ui_clean_211357.db` 备份恢复，
删掉当时残留的 `seq=135`，`verify` 通过（哈希链自校验确认恢复完整）。
**因为每轮对话都有哈希链，损坏是可检测的** —— 这一点救了这次事故。

### 15.5 修复：让「写错地方」不再静默发生

**光修路径不够 —— 根本问题是「写错地方时没有任何提示」。** 所以加了两样：

**① `storage.redirect_db(path)`** —— 显式的换库入口。
函数文档里写清了为什么不能在 `paths` 上赋值。换库时它会写一条运行日志。

**② `storage.connect(for_test=True)`** —— 破坏性测试的守卫。
它会**拒绝连接真实数据库**，逼你先 `redirect_db()` 到副本；
要强行放行得设 `DSH_ALLOW_REAL_DB_WRITE=1`（逃生门）。

**守卫的第一版我写错了**：用「行数 ≥ 100 判定为真库」，
结果**副本也是从真库复制的、行数一样（134 行）**，
于是「切到副本后」也被误拦。改用**路径 + 是否重定向过**判断，才正确。

实测四种情形：

| 情形 | 结果 |
|------|------|
| 真库 + `for_test=True` | ✅ 拒绝 |
| 切到副本后 + `for_test=True` | ✅ 放行（副本行数相同也不误判） |
| 设 `DSH_ALLOW_REAL_DB_WRITE=1` | ✅ 放行（逃生门有效） |
| 普通调用（不带 `for_test`） | ✅ 不受任何影响 |

### 15.6 教训

**「我以为在副本上跑」不等于「真的在副本上跑」。**
这次错误不报错、不提示、静默写错地方 —— 比崩溃危险得多。

三条可复用的做法：

1. **重定向要有显式入口，并且验证它真的生效**（我这次验了，才发现之前那版没生效）
2. **破坏性操作要有守卫，而守卫本身也要测**（我的第一版守卫就是错的）
3. **备份救了命** —— 事故前刚好做过备份。「动数据前先备份」这条纪律确实有用
