### 3.1 已实现的机制清单

- **只追加落盘**：`storage.py` 全文件无任何 `UPDATE` / `DELETE` 语句（已逐行确认），只有 `INSERT`
- **唯一 ID**：`turn_<12位hex>`、`raw_event_<8位hex>`
- **双时间戳**：每条记录同时存 UTC 与本地时间
- **对话哈希链**：每条记录覆盖前一条的 `sha256` + `content_hash`
- **内容哈希独立**：能区分「对话内容被改了」与「前后有增删」，报错信息更具体
- **事件文件 + `.sha256`**：一事件一 JSON，另存独立校验文件
- **人格运行期守护**：`assert_persona_unchanged()` 每轮比对人格文件 SHA256，被改即中止会话
- **成本账本**：调用写入 SQLite `api_calls` 表 + `logs/ledger.jsonl`，金额用**微元整数**累计避免浮点误差
- **人格哈希留痕**：每轮对话都记录当时的 `persona_sha256`，可追溯人格是否换过

## 五、代码缺陷（3 处，均可复现）

### 5.1 `python -m main` 不能用，但注释声称可以

`src/main.py` 第 18–19 行注释：

> 保证 `python src\main.py` 与 `python -m main` 都能正确 import 同目录模块

**实测**：

| 调用方式 | 结果 |
|---------|------|
| `cd C:\` 然后 `python <绝对路径>\src\main.py verify` | ✅ 通过（`sys.path.insert` 生效） |
| `cd C:\` 然后 `python -m main verify`（`src` 在 PATH） | ❌ **`No module named main`** |

**原因**：`sys.path.insert(..., Path(__file__).resolve().parent)` 只在脚本**已能被加载**之后才执行。`python -m main` 的模块解析发生在更早阶段，此时 `src/` 不在 `sys.path` 中。

**影响**：低（README 和所有文档都只推荐 `python src\main.py`，那条路是好的）。但注释是错的，会误导后来者。

### 5.2 `selftest --clean` 会静默删除 `memory/raw/events/说明.txt`

`selftest.py` 第 189–190 行：

```python
for path in list(RAW_EVENTS_DIR.glob("*")):
    path.unlink()
```

`glob("*")` 会连**非事件文件**一起删。本次实跑后，归档清单里登记过的 `memory/raw/events/说明.txt`（sha256 `3e214f67739ef3aa…`）**确实消失了**。

**影响**：目录占位符本身无害，但这是一个「清理逻辑比它该清理的范围更大」的模式。同类风险：如果将来有人把说明、索引或人工笔记放进 `raw/events/`，跑一次 `selftest --clean` 就会被无声删掉。

**当前处置**：我已重新放回一个同名占位文件。但**我无法还原原始字节** —— 新文件 sha256 为 `ba8a7ad58b1ccd7910931a30473c13b5a54ee9c10e21c53c28020c62fd442c60`，与清单登记的 `3e214f67739ef3aa…` **不一致**。归档清单中该条目现已失效，需要你决定是更新清单还是采用别的内容。

### 5.3 哈希链不自证，且文档已承认边界

`verify.py` 的校验逻辑是**用当前行数据重新计算哈希，再和当前行的哈希字段比**。这意味着：能改数据库的人，也能把整条链重算成自洽的 —— 校验会通过。

文档（README 第 7 节、`storage.py` 注释）已诚实写明这个边界：「不会自动向后级联，需重算后续所有哈希才能瞒过」。

**结论**：这不是 bug，是**设计上的已知限制**，值得保留。但必须清楚它的定位 —— 它防的是**意外改动和低成本篡改**，不是防有决心的攻击者。做实验足够，不要当成密码学保证。

### 5.4 附带发现（非缺陷）

- `events.py` 的 `candidate_facts()` 函数**从未被任何代码调用**（死代码）。注释说明是给 Phase 4 留的锚点。
- `config/settings.json` 里的 `peak_hours` / `peak_days` **不参与计算**，真正生效的是 `pricing.py` 第 21 行硬编码的 `PEAK_WINDOWS`。配置文件里注释承认了这点，但两处重复定义仍是维护隐患 —— 改 `settings.json` 不会改变高峰判断。
- `pricing.py` 的高峰判断只区分「工作日 + 时段」，**无法识别法定节假日**，需人工用 `LLM_PEAK` 环境变量强制。
- `selftest` 的假客户端模型名是 `fake-model-for-selftest`，未登记在 `cost.models` 里，所以自测会显示「4 次未计价调用」。这是**预期行为**，不是错误。
- `src/export_docs.py` 是独立的可选工具，不被主流程引用。
